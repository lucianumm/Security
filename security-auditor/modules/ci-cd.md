# MODULE — CI/CD, GIT AND THE SECURITY GATE

Scope: pipeline security, Git hygiene, and the permanent security gate this skill establishes.

Related: `supply-chain.md`, `secrets.md`, `docker.md`, `cloud.md`.
Standards: SLSA, NIST SSDF, OWASP Top 10 A08, CWE-1395, CWE-693.

---

## 1. Discovery

```bash
ls -d .github/workflows .gitlab-ci.yml bitbucket-pipelines.yml Jenkinsfile .circleci azure-pipelines.yml 2>/dev/null
grep -rn "uses:\|image:\|secrets\.\|\${{" .github/workflows 2>/dev/null | head -60
```

## 2. Pipeline security review

| Check | Requirement | Common finding |
| --- | --- | --- |
| Token permissions | Least privilege; GitHub: `permissions: contents: read` at workflow level, elevated per job only | Default write-all token → HIGH |
| Untrusted triggers | `pull_request_target`, `issue_comment`, `workflow_run` run with secrets and the base repo's permissions — never check out and execute PR code there | Fork PR code executing with secrets → CRITICAL |
| Script injection | `${{ github.event.pull_request.title }}` and similar interpolated into `run:` executes attacker-controlled shell | CRITICAL — pass through `env:` and quote |
| Third-party actions | Pinned to a full commit SHA, reviewed, minimal | `uses: some/action@main` → MEDIUM–HIGH |
| Secret scope | Environment-scoped secrets, production secrets only in protected environments with approvals | Production keys available to every branch → HIGH |
| Secret leakage | No `echo`/`set -x` of secrets, no secrets in artifacts, logs or error output; masking verified | — |
| Runners | Self-hosted runners not used for public fork PRs; ephemeral, isolated, patched | Persistent self-hosted runner reachable by forks → CRITICAL |
| Caches | Cache keys cannot be poisoned across branches; no secrets cached | Cache poisoning |
| Artifacts | Not public unless intended; no secrets, `.env` or source maps in published artifacts | — |
| Deploy approval | Production deploys require review/approval and are auditable | — |
| OIDC | Cloud auth via OIDC federation with a narrowly scoped trust policy instead of static keys | Long-lived cloud keys in CI → HIGH |
| Branch protection | Required reviews, required checks, no force-push to protected branches, signed commits optional | Unprotected default branch → MEDIUM |
| Concurrency/rollback | Documented rollback path; no deploy from a developer machine | — |

## 3. Git hygiene

```bash
cat .gitignore
git ls-files | grep -iE "\.env|\.pem|\.key|credentials|\.tfstate|\.sqlite|dump\.sql|node_modules/" | head
git log --oneline -20
git tag --list | head
```

- `.gitignore` covers env files, keys, local databases, build output, IDE files, coverage,
  `terraform.tfstate`, and OS junk.
- No secrets in tracked files or history (`secrets.md`).
- No large binaries or production data dumps in the repository.
- Release artifacts do not include source secrets or internal documentation.
- Commit signing and protected tags where the organization requires provenance.
- **Do not rewrite history during an audit** unless the user explicitly requests that exact
  operation; then inspect the remote ref and use compare-and-swap `--force-with-lease`
  (`../core/SAFETY.md` §3).

## 4. Security gate

Propose (in `AUDIT`) or implement (in `HARDEN`) a pipeline with these stages, adapted to the stack.
Starter workflow: `../templates/ci/github-actions-security-gate.yml` (GitHub) and
`../templates/ci/gitlab-security-gate.yml` (GitLab).

```text
1  lint
2  typecheck
3  unit tests
4  integration tests
5  secret scan            (gitleaks / trufflehog / provider scanning)
6  SAST                   (semgrep / CodeQL / language linters with security rules)
7  SCA / dependency audit (npm|pnpm|pip|composer|cargo|go|bundler audit, osv-scanner)
8  IaC scan               (checkov / tfsec / trivy config)   — when IaC exists
9  container scan         (trivy / grype)                    — when images are built
10 build
11 security regression tests   (the tests generated by this skill)
12 baseline comparison         (scripts/security-gate.sh against .security/baseline.json)
```

Keep it fast: run steps 5–9 in parallel; use incremental scanning on PRs and full scans on a
schedule (nightly/weekly) plus on release branches.

## 5. Blocking policy

The pipeline **must fail** on:

- a confirmed CRITICAL finding;
- an active secret detected in the repository or the diff;
- a confirmed authentication or authorization bypass;
- a confirmed RCE or SQL injection;
- a critical, reachable dependency vulnerability with no mitigation;
- a security regression against the baseline (a control that was `IMPLEMENTED` and no longer is);
- a failing security regression test.

HIGH findings block production deployment according to the project's policy — state the chosen
policy explicitly in `security/SECURITY_BASELINE.md` rather than leaving it implicit. MEDIUM and
below are reported, tracked and scheduled, not blocking.

Every gate needs a documented, auditable exception process (who approves, for how long, recorded in
`risk-register.json`) — otherwise teams disable the gate.

## 6. Machine-readable output

`CI_GATE` mode emits both a human summary and:

```json
{
  "result": "FAIL",
  "critical": 1,
  "high": 2,
  "medium": 4,
  "low": 7,
  "regressions": 1,
  "secrets": 0,
  "coverage": 0.83,
  "readiness": "NOT_READY_FOR_PRODUCTION",
  "findings": ["SEC-0003", "SEC-0011", "SEC-0019"]
}
```

Write it to `.security/last-audit.json` and to the job summary/artifact so trends are visible.

## 7. Continuous security model

```text
Developer change → Pull Request → security checks (incremental) → tests →
SAST / SCA / secrets → security regression tests → baseline comparison → PASS/FAIL → deploy
                                    ↓
                     nightly/weekly full audit + dependency updates
                                    ↓
                     release: full audit + production readiness verdict
```

Recommended cadence: incremental audit on every PR; full audit before a significant release,
periodically, after an incident, and after major architectural change (`../core/WORKFLOW.md`
§Change-aware).

Also propose a **Security Definition of Done** for every feature: input validated · authorization
enforced server-side · errors safe · security events logged · tests written · no secrets ·
dependencies scanned · regression test added where applicable.

## 8. Regression / verification

The gate actually fails on a seeded test finding (verify once, then remove the seed) · secret
scanning catches a canary pattern in a test branch · required checks are enforced by branch
protection · the workflow token has read-only default permissions · a fork PR cannot access secrets.
